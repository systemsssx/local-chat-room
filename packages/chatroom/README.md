# 聊天室（全栈）

注册一个账号 → 建一个房间 → 把 6 位房间码发给别人 → 群里实时聊天。

服务端 Python / FastAPI + SQLite，前端零构建（原生 ES Module），实时靠**一条 SSE 长连接**。
登录是**服务端会话 + 密码哈希**，房间之间靠**成员表 + 每次访问先验成员**做隔离。

## 二、三步上手

1. **注册**：用户名就是聊天里显示的名字，密码至少 8 位（注册完直接进，不用再登一次）；
2. **建房间**：点左栏的 **＋**，填房间名，选「凭房间码」还是「公开」；
3. **拉人**：右栏能看到房间码，点「复制」发给别人；对方点左栏的 **⌨** 输入这 6 位码即可加入。

同一个账号可以在手机和电脑上同时登录（两个会话互不影响），进同一个房间就能对着聊。

## 三、登录到底是怎么实现的

这是整个项目里最该讲清楚的一段 —— 因为"登录"很容易做成假的。

### 3.1 客户端只拿一张"门票"，认人靠服务端的名册

```
【登录】 浏览器 ──POST /api/auth/login {用户名, 密码}──► 服务端
                                                      ① 查 users 表，用盐 + 哈希验密码
                                                      ② 过了 → 生成随机 sid（256 位）
                                                      ③ sessions 表写一行：sid 的哈希 → user_id
         浏览器 ◄── 200 + Set-Cookie: sid=…; HttpOnly; SameSite=Lax ── 服务端

【之后】 浏览器每次请求自动带 Cookie: sid=…（fetch / EventSource 都自动带，不用写代码）
         服务端：拿 sid 的哈希查 sessions → 得到 user_id → 这才知道你是谁

        ★ user_id 是服务端**查出来的**，不是客户端**告诉它的**。
```

| 东西 | 谁生成 | 存在哪 | 客户端能改吗 | 作用 |
| --- | --- | --- | --- | --- |
| `user_id` | 服务端（users 表自增） | 服务端 | 能"自称"，但服务端不信 | 标识"是谁" |
| `sid`（Cookie 里的值） | 服务端随机生成 | 浏览器 Cookie + `sessions` 表 | 能看见、能删，但**伪造不了** | 用来换取 user_id |
| Cookie 这个机制 | 浏览器 | 浏览器 | —— | 自动携带凭据的载体 |

**为什么不能"客户端直接报 userId"**：HTTP 是无状态的，服务端每收到一句请求都相当于陌生人开口。
客户端能随便改的东西不能当身份 —— 改一行 JS 或敲一句 `curl -d '{"userId":1}'` 就能冒充别人。
所以接口里**根本没有 userId 这个入参**，消息的发送者由服务端从会话里填。

**为什么 Cookie 里装随机串，而不是直接装 userId**：Cookie 存在用户自己电脑上，用户随时能改。
装随机串时，改了就对不上名册；装 userId 时，改成 1 就冒充了管理员。

### 3.2 密码怎么存

`pbkdf2_hmac('sha256', 密码, 每个用户独立的随机盐, 200000 次)`，库里存成
`pbkdf2_sha256$200000$<盐hex>$<哈希hex>`；校验用 `hmac.compare_digest`（常量时间，防时序侧信道）。
**明文密码不落盘、不进日志、不回传给前端**。

### 3.3 Cookie 上的三个开关

| 属性 | 挡什么 |
| --- | --- |
| `HttpOnly` | JS 读不到 → XSS 也偷不走这张票 |
| `SameSite=Lax` | 别的网站发起的请求不带它 → 挡 CSRF |
| `Secure` | 只在 https 下发送（局域网 http 演示必须关掉，否则 Cookie 直接不落地） |

### 3.4 会话生命周期

- **有效期 7 天**，剩余不足 3 天时每次访问自动续期（滑动续期）—— 正常用的人不会被踢出去，闲置的票自然失效；
- **登出**要两边都清：删掉 `sessions` 那一行（票作废）+ 清浏览器 Cookie；
- **踢人**：删掉某人所有 session 行，他的所有设备立刻掉线（历史消息归属不受影响）；
- **登录限速**：同一用户名连续失败 5 次锁 60 秒；且"用户名不存在"和"密码错"给**同一句提示**。

### 3.5 为什么没用 JWT、也没把 token 放 localStorage

- JWT 无状态、不用查表，但**撤销麻烦**（要黑名单，又回到存东西）；服务端会话"删一行就作废"，更适合聊天室；
- `localStorage` 里的东西 JS 随便读（XSS 一偷就没了），而且 `EventSource` **不支持自定义请求头** ——
  `Authorization: Bearer` 根本带不上去。Cookie 是浏览器在 fetch / EventSource 上都会自动带的东西。

## 四、房间与数据隔离

### 4.1 一张表说清"谁在哪个群"

```sql
users(id, username UNIQUE, pass_hash, created_at)
sessions(sid_hash PK, user_id, created_at, expires_at, last_seen)     -- 名册
rooms(id, code UNIQUE, name, owner_id, visibility, created_at)        -- 房间实体
room_members(room_id, user_id, role, joined_at, last_read_seq)        -- ★ 进群 = 这一行
messages(id, room_id, seq, user_id, at, type, text, file_json)        -- seq 是"房间内"递增
```

**进群 = 往 `room_members` 插一行；退群/被踢 = 删那一行。** 房间码（`rooms.code`）只是"入群凭证"。

### 4.2 房间码

6 位，字符集 `ABCDEFGHJKMNPQRSTUVWXYZ23456789` —— **去掉了 `0 O 1 I L`**（念出来会搞混的字符）。
唯一索引兜底 + 撞了就重生成；**不用自增 id 当码**（顺序号能被一路试过去）；房主可以一键重置（旧码立刻失效）。

### 4.3 隔离不是"一个群一个数据库"

- **不是**一房一库、也不是一房一张表 —— 那样连接、备份、迁移都会翻倍复杂，收益接近零；
- 是**一张 messages 表，每行带 `room_id`**，隔离靠两件事：
  1. **数据隔离**：查询永远带 `room_id`（走 `idx_messages_room_seq` 索引）；
  2. **权限隔离**：访问前先问一句"你是这个房间的成员吗"。
- 权限检查**收口在一个函数**里（`rooms.require_member()`），所有路由都过它 ——
  漏写一个 `WHERE room_id` 或漏一次成员检查，就是越权读别人的群，所以不能靠"每条路由自觉"。

### 4.4 未读数怎么算

不需要单独存计数：`未读 = 房间最大 seq − room_members.last_read_seq`。
进房间（拉快照）时后端把 `last_read_seq` 推到最新，角标自然清零；自己发的消息也会顺手更新自己的已读位置。

### 4.5 上传的文件，谁能下载

`uploads/` 目录**不是**用静态目录挂出去的（那样等于开了一个不要登录的公开图床）。
下载走 `GET /uploads/{文件名}`，三道关卡：

1. **先验登录**，再验"你是不是这个房间的成员"（`uploads` 表记着每个文件属于哪个房间）；
2. **非图片一律当附件发**（`Content-Disposition: attachment` + `text/plain` + `X-Content-Type-Options: nosniff`）；
3. **上传只收白名单扩展名**，`TEXT_EXT` 里**故意没有 `.html` / `.svg` / `.xml`** ——
   它们会被浏览器当页面或脚本执行，放进同源目录就是**存储型 XSS**：别人打开链接，
   脚本就在我们的源里跑，能直接读走他的 Cookie。

还有一条：消息里的 `file` 字段（URL、文件名、预览…）是客户端拼的 JSON，
服务端**按白名单重建**后才入库 —— URL 必须是本服务上传接口返回的地址，而且那个文件确实传到了这个房间。
不然别人可以塞一个 `javascript:` 地址或指向别的群的文件。

## 五、实时：为什么只留 SSE

| | 下行 | 上行 | 结论 |
| --- | --- | --- | --- |
| HTTP 轮询 | 每 1.5s 拉一次 | POST | 费流量、实时性差 |
| **SSE** | 一条 `EventSource` 长连接，服务器主动推 | POST | **采用**：够用、自带断线重连、代码量最小 |
| WebSocket | 同一条连接双向 | 走 socket | 双向确实更强，但聊天室的上行本来就是普通 POST，用不上 |

**一条连接同时订两个频道**：`GET /api/sse?room=<id>`

| event | 什么时候来 | 前端做什么 |
| --- | --- | --- |
| `hello` | 连接建立 | 拿到我的身份、房间成员、最新序号 |
| `messages` | 这个房间有新消息 | 按 seq 去重后追加到窗口 |
| `members` | 成员进出 / 上下线 | 刷新右栏在线名单 |
| `rooms` | **我的房间列表**变了（被拉进群、被踢、房间改名换码） | 整表替换左栏 |
| `room-updated` | 别的房间有新消息 / 人数变了 | 只改那一行的未读数与摘要 |
| `ping` | 每 20 秒 | 心跳，防长连接被中间设备掐断 |

三个实现要点：

1. **seq 去重**：服务端给每条消息一个"房间内单调递增"的 seq，窗口只认它 ——
   同一条消息可能从 POST 响应和 SSE 两路到达，只显示一份；断线重连后服务端会重发差额，也不会重复；
2. **慢客户端不拖累别人**：每个连接一个 `asyncio.Queue`，广播方只往队列里塞字符串就返回，
   队列满了就丢它自己那条（`_safe_put`），绝不阻塞广播；
3. **在线 = 有活跃 SSE 连接**：不再靠"最近 15 秒有没有动静"猜，长连接在就是在线。

**分工不能互相替代**：单元测试跑得快、覆盖边界（正好 64KB、重复入群、过期会话、队列满），
端到端验证"整条链路真的通"（真 HTTP、真 SSE、真 Cookie、真 SQLite）。

> 端到端为什么不用浏览器：这台机器上浏览器自动化起不来（浏览器多进程 IPC 需要命名管道，
> 沙箱里被拒绝）。所以端到端用**纯 HTTP** 验证服务端，浏览器里的视觉与交互由
> [手动测试清单.md](手动测试清单.md) 兜底 —— 两层都跑一遍才算验完。
>
> 另外：**单元测试里不去读 SSE 的流**（它永远不结束，读它会挂住），
> 那一层只测"连不上的三种情况"和订阅表的推送范围，真正的推送由端到端验证。

## 九、已知问题 / 没做的

1. **私聊、@提及、消息撤回、表情**都没做 —— 题目要的是"房间内实时聊天"，这几样属于加分项；
2. 消息列表**没有虚拟滚动**，一个房间几千条会变卡（内存里只留最近 500 条，更早的翻页查库）；
3. 上传的图片**没有服务端缩略图**，大图直接原图下发；
4. **公开房间只有接口（`/api/rooms/public`），前端还没做浏览页** —— 目前一律凭码入群；
5. 上一版那个"**剪贴板监听模式**"去掉了：聊天室用不上，且它只能在 `localhost`（安全上下文）下工作；
6. 房间人数上限 200、单条文字 64KB、单文件 2MB —— 都是硬限制，写在 `app/config.py`；
7. **没有 HTTPS**：局域网 http 演示时 `Secure` 开关必须关；真要上公网，前面挂一层反向代理（nginx/Caddy）再打开 `COOKIE_SECURE=1`；
8. **没有找回密码**（没有邮箱系统），忘了只能重新注册；
9. 限速只做了"登录失败锁定"，发消息没有节流。

**踩过的坑（都写进代码注释了）**

- **同一件事两条路到达，后到的那次是空的**：自己发的消息既走 POST 响应、又走 SSE 推送，谁先到不一定。
  去重后第二次拿到的 `added` 是空数组，代码却还在读 `added[-1].at` —— 表现是
  **消息显示完全正常，但每发一条就弹一个红色报错**。这个 bug 只有真的在浏览器里点才会暴露：
  单元测试和纯 HTTP 的端到端都不经过渲染层；
- **上传 `.html` = 同源存储型 XSS**：一开始把 `.html` 放进了允许的文本扩展名里，
  上传后浏览器会用 `text/html` 内联执行它 —— 打开那条下载链接，脚本就在我们的源里跑，
  能直接读 Cookie。改法是把 `.html`/`.svg`/`.xml` 从白名单里删掉，**并且**把下载改成
  "验成员 + 非图片一律附件 + nosniff"。少收几种格式，比事后加一百个响应头省事；
- **`file` 字段不能整段信**：它是客户端拼的 JSON，可以塞 `url: "javascript:…"`、塞 3MB 的 preview。
  现在服务端按白名单重建，并要求那个文件确实上传到了这个房间；
- **公开房间列表里带房间码**：等于把邀请码贴在公告栏上，"凭码入群"就白做了 —— 现在列表里不给码；
- **`hub.frame` 不存在**：`frame()` 是模块级函数、不是 `Hub` 的方法。这个 bug 的恶劣之处是
  HTTP 状态码仍然是 **200**（响应头早就发出去了），前端只是一片安静 —— 是端到端脚本把它揪出来的；
- **并发进冷房间会丢消息**：两个请求同时载入同一个房间的内存副本，后写的把前一个桶覆盖掉，
  先拿到旧桶的那条消息就进了"孤儿桶"，`since()` 永远补不到它。现在 `_ensure()` 加了每房间的锁；
- **pbkdf2 不能跑在事件循环里**：20 万次哈希约 0.1 秒，直接在 async 路由里算，
  会把所有请求和 SSE 心跳一起卡住 —— 扔进线程池（`asyncio.to_thread`）；
- **单元测试里读 SSE 流会挂住**：SSE 的响应永远不会结束，`TestClient` 会一直等下去（实测跑飞），
  所以那一层只测不阻塞的部分；
- **自己发的消息被算成未读**：发完消息要顺手更新自己的已读位置（单元测试先红了才发现）；
- **`EventSource` 不能自定义请求头** —— 这是整个项目选 Cookie 而不是 Bearer token 的直接原因；
- **局域网 http 下 `navigator.clipboard` 不可用**（非安全上下文），所以"复制房间码"有兜底：
  退回选中 + `execCommand('copy')`，再不行就把码显示出来让人手抄。
