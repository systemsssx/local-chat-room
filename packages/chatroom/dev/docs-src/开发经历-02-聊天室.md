# 我的开发经历 · 局域网聊天室（全栈）

> 这次是拿上一个项目（协同剪贴板）当底子，改成一个**有登录、有房间、只有一条实时通道**的聊天室。
> 下面是我这边做过的事、卡住的地方，以及最后是怎么收尾的。

## 先把分工说清楚

| | 谁做的 |
| --- | --- |
| **定方向** | 我：只留 SSE、砍掉轮询和 WebSocket；左栏三种传输改成房间列表；房间号和昵称输入框全删；进群必须凭房间码；登录用 Cookie 会话 |
| **写代码** | AI：后端拆成 auth / rooms / db / 五个路由，前端重写成十个小模块，单元测试、端到端脚本、这份文档 |
| **抠概念** | 我：cookie 到底存在哪、sid 和用户 id 的区别、能不能拿 cookie 当用户 id、SQLite 怎么做到"隔离" —— 这四件事我一个一个问明白了才让它动后端 |
| **挑错** | 我：实测点出来一堆问题（页面打开是旧项目、每次发消息弹红条）。另外我还让一个**独立的复核**去挑刺，它挑出三个严重问题 |
| **没让 AI 干的** | 《项目说明》那篇是我自己手敲的，AI 不代笔 |

## 一、我做的几个决定

1. **只留 SSE**。三种传输里，轮询费流量、WebSocket 双向用不上（聊天室发消息本来就是普通 POST），
   留一个最好维护的。砍掉之后左栏那三个"通信方案"就没意义了 —— 所以左栏直接改成房间列表。
2. **房间和身份都从界面上挪走**。原来顶栏有"房间号输入框 + 进入"和"昵称输入框"，
   聊天室里房间应该从列表里选、身份应该来自登录，这两个输入框留着只会让人乱。
3. **进群凭房间码**。像游戏开房那样：建完房给一个 6 位码，发给谁谁能进。
   我特意确认过：码不能用自增 id（顺序号能被一路试过去），所以是随机生成、去掉容易念错的 `0O1IL`。
4. **登录用 Cookie 会话，不用 JWT**。理由很实际：`EventSource` 不支持自定义请求头，
   Bearer token 根本带不上去；Cookie 是浏览器在 fetch / EventSource 上都会自动带的东西。
5. **砍掉"剪贴板监听"模式**。那是上一个项目的能力，聊天室用不上，而且它只能在 `localhost` 下工作。

## 二、靠提问把"登录"这件事弄明白

这块我最不想含糊，因为登录最容易做成假的。我问了四轮：

### 例子一：cookie 是"握手成功的凭据"吗

**不是。** 握手（TCP/TLS）是传输层的事，请求发完就没了；HTTP 本身**没有状态**，
每一句请求在服务器看来都是陌生人开口。所谓"我登录了"这件事，是**服务端自己在
`sessions` 表里记的一笔账**：你出示的随机串对得上表里的行，才认你是那个人。

我自己的总结是：**cookie 是门票，服务端手里有名册**。保安不是看你的脸认出你，是拿编号去翻名册。

### 例子二：为什么 cookie 里不直接放用户 id

一开始我以为"反正服务端认的是用户 id，那 cookie 里装 id 不就行了"。**不行**，两个原因：

- cookie 存在**用户自己的电脑上**，用户想改随时能改（F12 里双击就能编辑）。装随机串时改了就对不上名册；装用户 id 时，改成 1 就冒充了管理员；
- 身份是**长期**的（跟账号同寿命），门票是**短期**的（几天过期、可以有好几张、要能随时作废）。
  拿票号当身份，等于"换张卡公司就不认识你了"。

这一条我自己有体会：**我爬虫里那张 cookie 就是几天要换一次**，跟这里是一回事。

### 例子三：那接口里还传不传用户 id

**不传。** 客户端只出示 cookie，服务端拿 cookie 查出用户 id —— **id 是服务端查出来的，不是客户端告诉它的**。
所以现在发消息的请求体里没有 `userId`、没有昵称，署名一律由服务端填。

### 例子四：SQLite 怎么"隔离"

我原本以为要"一个群一个数据库"。AI 的解释让我改了主意：**不是一房一库，是一张表 + 每行带 `room_id`**，
隔离靠两件事 —— ① 查询永远带 `room_id`；② 访问之前先问一句"你是这个房间的成员吗"。
一个群一个库会让连接、备份、迁移全部翻倍复杂，收益接近零。

**真正会出事的是"忘了加 WHERE"或"漏了一次成员检查"**，所以这一条我要求**收口成一个函数**，
所有路由都过它，不许每个路由各写一遍。

## 三、界面：先出设计稿，再动手

按老规矩，代码之前先要一版**能看的设计稿**。这次的改动在结构上：

| 位置 | 改成 |
| --- | --- |
| 左栏 | 三种传输方式 → **房间列表**（房间名 + 人数 + 最后一条摘要 + 未读角标） |
| 顶栏 | 房间号/昵称输入框 → **当前房间铭牌 + 我 + 退出登录** |
| 消息行 | 去掉 POLL/SSE/WS 管道标记，位置让给头像 |
| 右栏 | 去掉"历史记录"卡片（消息流本身就是历史），换成成员 / 房间概况 / **房间码** |
| 新增 | 登录卡片、**建房间与加入房间弹窗**（和登录卡片同一套样式） |

设计稿我看了之后提了几处（消息正文太宽、右下角切换条挡内容、成员列表里"正在输入"挂在我不对），
改完才落到 `public/` 里实现。配色和字形沿用原来的"精密仪表"皮肤 —— 改动量小，也是已经验收过的风格。

## 四、结构上最重要的一件事：把权限收口

后端所有涉及房间的接口，第一步都是同一个函数 `require_member(room_id, user_id)`：

- 不是这个房间的成员 → 一律 403；
- 快照、发消息、翻页、上传、SSE、房间详情、连接实况、退群、换码、解散 —— **11 个入口逐个查过**，
  没有一个能绕过去。

这件事最后是被一份**独立的复核报告**确认的（它把 11 个入口一个一个打了标记），
不是我自己说"我写了"就算数。

## 五、测试：这次多了一层

| 层 | 数量 | 测什么 |
| --- | --- | --- |
| 单元测试 | **131 项**（约 4 秒） | 认证、会话、房间、成员、消息、上传下载、SSE 订阅表 |
| 静态检查 | 66 个 id | JS 用到的元素 id 在两份页面里都在，且两份一致 |
| 端到端 | **51 项** | 对着真服务器跑完整流程（纯 HTTP） |

**端到端为什么不用浏览器**：这台机器上浏览器自动化起不来（多进程 IPC 要命名管道，被环境挡了）。
所以端到端改成纯 HTTP 跑服务端，**浏览器里的东西用手动测试清单兜底** ——
这个分工后来被证明是对的，也暴露了一个只有手点才能发现的 bug（见下一节）。

## 六、独立复核抓出来的三个严重问题

我让一个独立的复核去挑刺（只读、不许改文件），它挑出来的东西比我预期的多：

1. **上传 `.html` = 同源存储型 XSS**。我一开始把 `.html` 放进允许的文本扩展名里了，
   上传后浏览器会按 `text/html` **内联执行**它 —— 别人打开那条下载链接，脚本就在我们的源里跑，
   能直接读走 Cookie。改法有两层：白名单里删掉 `.html/.svg/.xml`，**并且**把下载改成
   "验成员 + 非图片一律当附件 + nosniff"，同时 `uploads/` 不再用静态目录挂出去（否则连登录都不用就能下载）。
2. **公开房间的列表里带着房间码**。等于把邀请码贴在公告栏上，"凭码入群"成了一句空话。现在列表不给码。
3. **消息里的 `file` 字段整段信客户端**。那是客户端拼的 JSON，可以塞 `url: "javascript:…"`、
   塞 3MB 的预览。现在服务端按白名单重建，并要求"那个文件确实上传到了这个房间"。

还有四个中等问题：切房间的竞态、并发进冷房间会丢消息、被移出房间后 SSE 静默死掉、
pbkdf2 跑在事件循环里把所有请求堵住。这些都在当天修完，并且各自补了回归测试。

## 七、我自己实测才发现的那个 bug

修完之后我自己开两个窗口测。结果出现一个很烦的现象：**消息一切正常，但每发一条就弹一个红色的报错条**。

查下来根因挺有意思：

```
我发消息 → 服务端存下 → 同一件事从两条路回到前端：
   ① SSE 推给我（先到 —— 消息立刻显示）
   ② POST 的响应（后到 —— 同一条消息，被 seq 去重后剩下一个空数组）
   代码没挡住"去重后为空"，于是去读 空数组[-1].at → 抛异常 → 被 catch 接住 → 弹红条
```

这个 bug **单元测试和端到端都抓不到**（它们不经过渲染层），只有真的在浏览器里点才会暴露。
我把它记进 README 的"踩过的坑"了 —— 它正好说明为什么"能在浏览器里点一遍"这件事不能省。

顺带我还发现自己看错了一次：页面打开的其实是**早上那个旧项目的标签页**（浏览器恢复了它），
它还在按老接口轮询，新服务端回它一句"房间不存在"。后来我给页面加了 `no-cache`，
以后改前端不会再出现"我改了、浏览器还是旧的"。

## 九、还没做好的地方

1. **私聊、@提及、撤回、表情**都没做 —— 题目要的是房间内实时聊天，这几样属于加分项；
2. 消息列表**没有虚拟滚动**，一个房间几千条会变卡（内存里只留最近 500 条，更早的翻页查库）；
3. **公开房间只有接口，前端还没做浏览页** —— 目前一律凭码入群；
4. 上传的图片**没有服务端缩略图**，大图直接原图下发；
5. **没有 HTTPS**：局域网演示时 Cookie 的 `Secure` 开关必须关掉；真要上公网，前面得挂一层反向代理；
6. **没有找回密码**（没有邮箱系统），忘了只能重新注册；
7. 限速只做了"登录失败锁定"，发消息没有节流。

## 最后

上一个项目我是"边做边学"，这一次是"先把概念问清楚再动手"，效果好得多 ——
尤其是登录和隔离这两块，问明白之后，后面所有的代码都在同一个逻辑上，没有再返工。
