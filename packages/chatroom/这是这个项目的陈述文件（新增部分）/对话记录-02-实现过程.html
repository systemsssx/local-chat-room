（按"登录鉴权"理解）这块要拆成三条线：身份（注册/登录）、凭证（登录后发什么、之后每次请求怎么带）、校验（服务端怎么验、怎么防越权）。下面说这套项目里该怎么落。

一、结论先给：Cookie + 服务端 Session 表 + 密码哈希

三个选择里，这个方案在你的项目里有一个决定性优势：

你有 SSE，而前端的 EventSource 不能自定义请求头 —— 想带 Authorization: Bearer xxx 是带不上的（只能退而求其次塞 URL 参数，那 token 会漏进访问日志）。WebSocket 握手同理，虽然能塞子协议但很别扭。 Cookie 是浏览器在所有三种传输上都会自动带的东西：fetch、EventSource、new WebSocket() 全都带。所以三套传输共用一套凭证，一行额外代码都不用写。

方案长什么样适合吗
服务端 Session（推荐）服务端发随机 token，存 sessions 表；Cookie 里只放这个随机串✅ 可随时撤销（登出/踢人）、三种传输自动带、无需额外库
JWT签名令牌，服务端不存⚠️ 得引 PyJWT；撤销麻烦（要么黑名单表、要么短过期+刷新，等于又回服务端存东西）；收益是"无状态"，你单机 SQLite 根本用不上
前端存 token 自己塞头localStorage + Authorization❌ SSE 走不通；且 localStorage 里能被 XSS 读走

二、三块具体怎么实现

1. 密码怎么存 —— 不可逆哈希 + 每个用户独立盐

绝不能明文，也不要用 md5/sha256(密码) 裸哈希（彩虹表/GPU 爆破）。两个选项：

  • 零新依赖（贴合你现在"非标准库只有 4 个"的风格）：hashlib.pbkdf2_hmac('sha256', pw, salt, 600_000)，盐用 secrets.token_bytes(16)，校验用 hmac.compare_digest（常量时间，防时序侧信道）。
  • 更省心：pip install bcrypt，bcrypt.hashpw / checkpw，迭代参数由库自己管。

说白了就一句：库里存的是"算不回去"的东西。面批被问"密码怎么存的"，这一句就是满分答案。

2. 登录成功后发什么 —— 一张 sessions 表

users(id, username UNIQUE, pass_hash, salt, created_at)
sessions(token_hash, user_id, created_at, expires_at, last_seen)
  • token 用 secrets.token_urlsafe(32) 生成，库里存它的哈希（库被拖走也不能直接冒充登录）；
  • 响应里 Set-Cookie: sid=...; HttpOnly; SameSite=Lax; Path=/，上公网（HTTPS）时再加 Secure；
  • HttpOnly = JS 读不到，XSS 也偷不走；有效期 + 每次访问滑动续期（或 7 天固定过期）。

3. 服务端怎么验 —— 一个依赖，挂在所有要保护的接口上

FastAPI 就一个函数的事：读 Cookie → 查 sessions → 查 users → 返回当前用户；验不过就 401。

POST /api/auth/register   → 建用户（用户名唯一、密码规则）
POST /api/auth/login      → 校验密码 → 建 session → Set-Cookie
POST /api/auth/logout     → 删 session
GET  /api/auth/me         → 当前是谁（前端启动时问一次，决定显示登录页还是聊天页）

三、几个必须知道的边界（也正是面批会追问的）

  1. 认证 ≠ 鉴权：认证=你是谁（登录）；鉴权=你能干什么。你这题的实际鉴权规则就三条：未登录不能发、只能以自己的身份发（不能伪造别人昵称）、房间数据按房间隔离。
  2. CSRF：SameSite=Lax 已经挡住跨站 POST 带 Cookie；加上你的写接口收的是 application/json（跨站表单发不出来，会触发预检）——够用。要更严就加个 CSRF token 或校验 Origin。
  3. 登录限速：同一用户名连续失败计数 + 短暂锁定，防爆破。几行代码，很加分。
  4. token 绝不进 URL（SSE 场景最容易这么干，别干）。
  5. HTTPS 才有 Secure Cookie：局域网 HTTP 演示时不要加 Secure，否则 Cookie 直接不落地 —— 这也是"局域网照样能演，公网部署时才加"的一个开关。

① 输入用户名密码后就"产生"一个 cookie 吗？

顺序对了一半 —— cookie 不是浏览器凭空产生的，是服务端发的、浏览器替你收着。登录那一次发生的事情是：

浏览器 ──POST /api/auth/login  {用户名, 密码}──► 服务端
                                              ① 查 users 表，拿盐 + 哈希验密码
                                              ② 验过了 → 随机生成一串 sid（比如 32 字节）
                                              ③ 往 sessions 表写一行：sid → 用户 id、过期时间
浏览器 ◄── 200  +  Set-Cookie: sid=abc123…; HttpOnly; SameSite=Lax ── 服务端
              ↑ 重点是响应头里这一行，浏览器看到它才会把 cookie 存下来

注意几个细节：

  • 密码只在这一次请求里出现过，验完就丢；服务端只留哈希，cookie 里也没有密码、没有用户名，只有那串随机数；
  • 这串随机数本身没有含义，它就是个"编号"，含义全在服务端的 sessions 表里；
  • 之后每一次请求，浏览器会自动加上 Cookie: sid=abc123…，不用你写任何代码。

② 用这个 cookie 才能"进入网页"吗？

这里要纠正一个常见误会：cookie 不是"打开网页"的钥匙，是"接口认不认你"的钥匙。

没 cookie 会怎样
拿 index.html / CSS / JS照样能拿到 —— 这些是公开文件，谁都下得走
问 /api/auth/me（我是谁）返回 401
发 POST /api/messages（发消息）返回 401/403，消息发不出去

前端启动时先问一次 /api/auth/me：401 就画登录页，200 就画聊天页。所以"能不能进"是前端根据接口的回答画出来的，不是服务器把网页锁起来了。

想做到"没登录连 HTML 都不给"，那叫服务端重定向（看到没 cookie 就 302 到 /login），是另一种做法；单页应用一般不用，因为前端本来就要靠接口判断。

③ cookie 存在用户端吗？

属性作用
HttpOnlyJavaScript 读不到 —— 就算页面被 XSS 注入，也偷不走这个 cookie
SameSite=Lax别的网站发起的请求不带它 —— 挡 CSRF
Secure只在 https 下才带（局域网 http 演示时不能加，加了 cookie 直接不落地）

还有两个实际会碰到的点：

  • 按域名隔离，但不按端口：localhost:8000 和 localhost:9000 共用一份 cookie；但 localhost 和 192.168.1.14 是两个不同的域名，cookie 不通用 —— 你电脑上登录了，手机连局域网 IP 打开还得重新登录，这是正常的；
  • 不设过期时间 = 会话 cookie，关浏览器就没；设 Max-Age=604800 = 存磁盘，七天内在还在。

这里是第二个要纠正的地方 —— "握手"这个词有两层，别混在一起：

握手是什么和登录有关系吗
TCP / TLS 握手传输层把连接建起来，请求发完连接就关了没关系，那是每次请求都可能发生的事
"登录状态"HTTP 协议本身是无状态的协议里根本没有这回事

HTTP 无状态的意思是：每一句请求在协议看来都是陌生人开口，服务器不记得你上一句说过什么。所谓"我登录了"这件事，完全记在服务端自己的一张表里：

浏览器手里的：sid = abc123…          ← 只是张门票，上面只有编号
服务端表里的：abc123… → 用户 7 号，10 月 14 日过期   ← 名册，认不认由它说了算

所以更准确的说法是：cookie 是门票，服务端手里有名册。保安不是"看你的脸认出你"，而是拿编号翻名册。

这也顺带解释了另外三件事：

  • 为什么能"踢人"：把名册上那一行划掉，那张票立刻作废 —— 这就是"服务端会话"比 JWT 好用的地方；
  • 为什么登出要通知服务端：光删浏览器里的 cookie 不够（服务端那张票还能用），要两边都清；
  • 为什么前端说"我登录了"不算数：前端说的话谁都能改，状态只能放在服务端。

串起来一句话

登录 = 服务端验一次密码，然后在自己表里记一笔，顺手给浏览器一张写着编号的门票；之后浏览器每次请求自动出示门票，服务端拿编号翻表——表上有，就认你。

面批要是问"你的登录是怎么实现的"，照这句说一遍就行，接着补一句：密码是 pbkdf2 哈希加盐存的，cookie 是 HttpOnly + SameSite=Lax，登出就把 sessions 表那行删掉。

做法评价
每个群一个 .db 文件（ATTACH DATABASE 或按群分文件）❌ 能做但不该做：连接管理、备份、迁移、跨群统计全部翻倍复杂，收益接近零。群里几万条消息，SQLite 单文件毫无压力
每个群一张表（messages_3、messages_4…）❌ 更不该做：建表要动态拼 SQL，索引和迁移全乱
一张 messages 表，每行带 room_id✅ 正解，微信/QQ/Slack 都是这么干的

所谓"隔离"实际是两件事，别混：

① 数据隔离 —— 靠查询条件 + 索引

SELECT * FROM messages WHERE room_id = ? AND seq > ? ORDER BY seq LIMIT 50;
--                     ^^^^^^^^^^^^^^^ 永远带着它
CREATE INDEX idx_messages_room_seq ON messages(room_id, seq);   -- 你已经有了，改列名即可

② 权限隔离 —— 每次访问前先问一句"你是这个群的人吗"

def require_member(room_id: int, user_id: int) -> None:
    if not db.is_member(room_id, user_id):
        raise HTTPException(403, "你不在这个房间里")

这才是真正的风险点：数据库本身没问题，出事的永远是某个路由忘了加 WHERE room_id 或忘了查成员，于是别人能读到不属于他的群。所以别在八个路由里各手写一遍，收口到一个函数，所有读房间数据的地方必须先过它。这一条比"用什么数据库"重要得多，也是面试官最想听的答法。

另外别把两个"隔离"搞混：SQLite 的 WAL / 事务 / 写锁管的是并发和一致性（你现在的 _lock 就在干这个），不是权限。

一、user_id 的本职：给"这个人"一个稳定的代号

数据库里凡是"谁干的"地方，都要指向同一个人：

messages.user_id        这条消息谁发的

rooms.owner_id          群是谁建的

它只需要满足三点：短、不变、没含义（数据库里叫"代理键"）。短是顺带的，不变才是关键。

顺带一句：所以也不要用用户名当主键 —— 用户名能改，一改所有历史归属就断了。

二、为什么不拿 sid 当 user_id：寿命不一样

user_id（员工号）sid（门禁卡号）
和人的关系一个号 = 一个人一个人可以有好几张卡（手机一张、电脑一张、无痕一张）
活多久跟账号同寿命几天就过期
会变吗永远不变每次重新登录都换一张
要能失效吗不能（历史数据都指着它）必须能（登出、被踢、改密码）

这是本质区别：sid 是"会消失的东西"，不能拿去当"要长期存在的东西"。

三、真拿 sid 当 user_id，会出什么事

假设阿哲在电脑和手机上各登录了一次：

sessions:  abc… → 7      （电脑）

如果拿 sid 当 user_id：

messages:     seq=101  user_id=abc…   ← 阿哲的电脑
              seq=102  user_id=xyz…   ← 阿哲的手机      ✗ 同一个人的消息裂成两份

这是拿一次索引查询换来的东西，非常划算。
