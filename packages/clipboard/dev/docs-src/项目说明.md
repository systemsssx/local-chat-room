# 项目说明（我自己的理解）

> 纯手敲的，没打草稿。下面是我对这个项目本身的理解，跟交付物的口径可能有出入，以这篇为准。

我这个项目分服务端和客户端两部分：服务端用 sqlite 做数据源，所有用户端先把数据传到服务端，
服务端再把数据传回各个用户端。三种传输方式的区别，就产生在"传输"这一步。

最简单的是轮询，数据是用户主动向服务器要的 —— 页面每隔固定间隔发一次请求，判断有没有更新。
这个方法我之前那个项目也用过，不过当时打交道的对象不是网页和服务器：那时候是为了判断一个窗口
是不是不再变化了，做法是轮询截图，再拿截图去比对（大概是比对字节数吧，记不太清了），
运行过程中还要顺手清理截图缓存，只留最近三张。这段算是题外话。

轮询要往服务器传东西时，走的是另一条通道 —— 轮询和 SSE 的上传其实是一回事，都是普通的 HTTP POST。

SSE 就明显高级一点：服务器收到新消息之后，由服务器主动发到各个客户端。
我理解它本质上就是一个逻辑判断，一个 if 分支（我是这么理解的）。

最后是 WebSocket，它把上传和发送做成了一条通道，双向都走同一根管子，效率上确实高不少。
不过它不适合拿来传文件 —— 题目里也明确说了不用 WebSocket 传二进制，所以文件还是单独走 HTTP 上传。

关于传文件，我还特意问了一下什么叫分帧。简单说：我们传给服务器的是一长串字节，
中间虽然分了好几个字节段，但这些段并不是按消息切的；要让服务器知道哪几个字节属于同一条消息，
就得靠分帧。常见的做法有四种：定长、长度前缀（在每条消息前面加两三个字节，
先告诉程序这条有多长）、加分隔符、加结束标识。

我第一印象觉得第三、第四种更合理，比较符合人的直觉；结果挺意外 ——
现在最主流的居然是第二种（长度前缀），后两种作为补充。当然这也是题外话。

总而言之大概就是这个逻辑。各个用户是怎么连接到服务器的呢：一开始有一行调用操作系统的代码，
让操作系统去找服务器"握手"，等服务器回一句"哎呀，都是老乡"，握手就算成功、连上了。
这一点也挺意外的 —— 我一直以为向服务器发请求一定要有库撑着（比如 requests，
我之前写爬虫用得特别多），结果是系统调用层面一行命令的事。

至于为什么最后做成了聊天室而不是共享输入框：主要是本人土鳖，之前没见过这种交互模式，
写到一半发现是这么回事，已经来不及改了。

前端设计套用的是我之前的项目（架构是，风格不是），我自己还是挺满意的。

关于 P2P 那道题，我的理解是：可以做成网状连接，让用户和用户之间私下交易。
不过好像还是要过服务器，这一点我没太搞懂为什么（雾）。需要的东西是信令（用来过防火墙、
互相识别）和 WebRTC DataChannel（浏览器自带的功能）。但我做的是聊天室，
所以这个作用就不大了（喵喵）。

先这样了，这篇是纯手敲的，有点累。
