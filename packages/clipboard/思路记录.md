## 2026-10-06 · 前端架构：六个组合怎么共用一个信息窗口

**原话：**

> 没事了，你先写前端吧，我想的是六个板块的互通问题，怎么让六个板块共用一个信息窗口，切换的只是发送信息的模式（历史记录也是互通）。

**落实成的架构（三个正交概念）：**

| 概念 | 数量 | 职责 | 不许碰的东西 |
| --- | --- | --- | --- |
| 输入源 | 2（纯文字 / 剪贴板监听） | 产出待发送的消息，交给统一的 `send()` | 不碰窗口、不碰传输 |
| 唯一数据源 `MessageStore` | 1 | 按服务端 `seq` 去重合并；窗口只订阅它 | —— |
| 管道（传输） | 3（轮询 / SSE / WS） | 把消息灌进 store | 不知道窗口长什么样 |

- **切换传输**：停旧管道 → 新管道带 `since = store.lastSeq` 接上 → 窗口不清空、只补差额
- **切换模式**：只替换底栏 composer，不动 store、不动传输
- **历史互通**：历史就是同一份数据源在服务端的持久化副本，不是另一套数据
- **重复到达只显示一次**：同一条消息可能从 POST 响应 + SSE 推送 + WS 广播三条路都到，靠 `seq` 幂等合并

**实现结果（2026-10-06 端到端验证 18 项全通过、控制台零报错）：**
SSE 发一条 → 切轮询（窗口仍 1 条）→ 轮询发一条 → 切 WS（仍 2 条）→ WS 发一条 → 切模式（仍 3 条）；
消息行上标着每条是从哪条管道送出的（POLL / SSE / WS / CLIP）。

**依赖再修正：** `iconv-lite` 不需要了 —— 实测 Node 自带的 `TextDecoder('gb18030')` 可用。
最终非内置依赖只有 `express`、`ws`、`multer`。

## 2026-10-06 · 决定不做防抖

**原话：**

> 那就不要做防抖了，既然我都数据源（服务器）就不需要用这种低效的交互模式了

**沉淀出的约束：**

- **决定：不实现防抖（debounce）**；「纯文字」模式保持显式发送（Enter / 点发送）。
- ⚠️ **要修正的是理由，不是决定。** 「有服务器所以不需要防抖」因果是反的：
  防抖存在的唯一原因就是背后有服务器要照顾（别打爆服务端、别让别人的页面疯狂重绘）；
  真正让防抖**失效**的是**交互模型变了** —— 聊天式一次发送＝一条消息，不存在"每按一键发一条"。
- **验收话术（按这个说法讲）：** 题目的防抖针对的是"一个共享文本框边打边同步"那种交互；
  本实现改为显式发送，一次操作产生一条消息，防抖没有作用对象；本机剪贴板监听那条路径用的是
  "每 800ms 采样比对、变了才发"，属于去重 + 节流，同样不需要防抖。
- 代码里已有的同类机制：`app.js` 的 `scheduleHistory()`（900ms 节流，避免每条消息都去刷历史面板）。

## 2026-10-06 · 建库：SQLite 落地

**原话：**

> ok，现在建库吧，你告诉我库是什么形式的（csv吗，那图片怎么办），第二个他的接口是怎么接的

**问的三件事与结论：**

1. **库是什么形式** → **不是 CSV**，是磁盘上的**一个文件** `data/app.db`（内部 B-Tree + 页）。
   选它的理由：零配置、零安装、不是独立服务、整个库就是一个文件（拷走即备份）。
   Node 24 内置 `node:sqlite`，不装任何 npm 包。
2. **图片怎么办** → **图片不入库**。二进制放磁盘 `uploads/`，库里只存 URL 与元信息
   （大小、文件名、MIME）。规模放大后只是把"本地磁盘"换成对象存储（S3/OSS），思路一样。
3. **接口怎么接** → `node:sqlite` 的 `DatabaseSync` + `prepare()` 预处理语句 + `?` 参数绑定（防注入）。
   **关键：`src/rooms.js` 里 `roomStore` 的接口没变，所以上层 `src/routes/*` 一行都没改。**

**表结构（按题目提示分建两张表）：**

| 表 | 内容 |
| --- | --- |
| `rooms` | 房间当前状态：room / text / seq / updated_at / updated_by |
| `messages` | 历史记录：每条消息一行（含发送者、IP、管道、来源、文件 JSON） |

**持久化策略：** 启动取 `MAX(seq)` 接上序号（**不能让 seq 重置**，前端靠它去重）；
首次访问房间时载入最近 500 条进内存；每次发消息**先落库再进内存**（一个事务写两张表）；读历史直接查库。

**这一步抓到的 bug：** 冷房间第一次写消息时，如果先落库再载入内存，
消息会被"载入一次 + push 一次"→ 重复。修正顺序：**先 ensure 载入 → 再落库 → 再 push**。

**验收实测：** 写消息 → 杀进程 → 重启 → 接口读回，消息还在、seq 未重置；
`rooms` 表里房间当前内容与最后修改者都在；e2e 21 项回归全通过。

**原话：**

> 现在把六个功能绑上去把，要求可以写多个py文件，反正最后的结果我要很清晰的看到html mainjs py结构清晰

**沉淀出的约束：**

- **后端改用 Python**（题目首推的栈）：FastAPI + uvicorn + python-multipart，**拆成多个 .py 文件**。
- **最终结构要一眼看清**：`index.html` + `public/js/main.js` + 多个 `.py`。
  前端入口从 `app.js` 改名为 `main.js`。
- 六个组合（2 输入模式 × 3 传输）**全部绑到 Python 后端**。
- Node 版后端移到 `alt-node/`，不删除、留作对照，但不在主路径上。

**做法：前端一行没改。** 因为前端只认**接口契约**，Python 后端按同一套接口实现即可 ——
这正是之前把传输/模式拆开、把 `roomStore` 设计成接口的回报。

**Python 侧的三个实际差异（都实测过）：**

| 事情 | Node 版 | Python 版 |
| --- | --- | --- |
| multipart 中文文件名 | busboy 按 latin1 解，**要手动补一次 UTF-8 转换** | `python-multipart` **直接正确**，不用补 |
| GBK 文本 | `TextDecoder('gb18030')`（Node 内置 ICU） | `bytes.decode('gb18030')`（标准库） |
| SQLite | `node:sqlite`（内置） | `sqlite3`（标准库） |

**这一步修的坑：** JSON 响应要显式带 `charset=utf-8`。FastAPI 默认的 `application/json`
不带 charset，浏览器没问题，但 Windows PowerShell 5.1 的 `Invoke-WebRequest` 会退回按 latin1 解
→ 中文全变乱码（一度以为是数据存错了，直接查库才确认数据是好的）。另外服务端输出也显式设成 UTF-8，
避免输出被管道接走时按系统区域编码编码。

## 2026-10-06 · 手机适配版

**原话：**

> 你针对手机做一个适配版html

**沉淀出的约束与做法：**

- **单独一个 `mobile.html`**（而不是把桌面版硬改成响应式）：桌面版是四面框，手机上是
  「顶栏 + 组合条 + 全宽消息流 + 底部输入」，左右侧栏收进两个抽屉 —— 结构差异太大，各做各的更干净。
- **`index.html` 加一句窄屏自动跳转**（≤860px 跳 `mobile.html`，带 `?desktop` 可强制看桌面版），
  这样手机上永远只需要输一个根地址。
- **`main.js` 一行没改**：手机版把桌面上那 32 个 DOM id 原样保留（一部分藏进抽屉、一部分隐藏），
  「换管道 / 换输入源 / 发消息」的逻辑完全复用。**换布局只换 HTML 结构和 CSS。**
- 手机上做的适配：`100dvh`（避开地址栏高度跳动）、`env(safe-area-inset-*)`（刘海屏）、
  输入框字号 ≥16px（iOS 聚焦不放大）、触控目标 ≥44px、消息改成「发送者信息一行 + 内容占满宽度」。
- 传输方式在手机上用简称（轮询 / SSE / WS），否则组合条放不下会把「剪贴板」截掉。

**这一步抓到的两个 bug：**

## 2026-10-06 · 新消息自动滑到底部（修了一个一直没生效的 bug）

**原话：**

> 更新一个小点，现在有最新消息会下滑到底部

**查出来的 bug：** 自动滚动**一直是坏的** —— 代码在给 `#streamList` 设 `scrollTop`，
但真正带 `overflow-y:auto` 的滚动容器是它的父元素 `#msgs`。给一个不能滚动的 div 设 `scrollTop`
没有任何效果，所以"跟到底部"从来没生效过。

**修法：** 渲染器改成接收两个元素：`listEl`（消息塞进这里）和 `scrollEl`（真正滚动的是它）。

**顺带把行为做对（聊天类应用的通用做法）：**

| 情形 | 行为 |
| --- | --- |
| 你本来就在底部 | 新消息来了**自动跟着滚到底部** |
| 你翻上去看历史了 | **不硬把你拽下来**，浮出「N 条新消息 ↓」按钮，点一下才下去 |
| 首次载入历史 | 直接到底部 |

**第二个坑：图片是异步加载的。** 滚到底部的那一刻图片还没加载完，等高线定下来内容又变高，
人就"悬"在半空了。修法：**用 `ResizeObserver` 盯着内容高度，只要还贴着底部，高度一变就再跟一次**。

**追问与最终决策：**

> **原话**：为啥不直接拽下去
> **原话**：会啊（指出"自己发消息时其实会拽"—— 我上一句说得太绝对，在底部时确实会）

- **最终保留"智能跟随"**，不改成"永远拽到底"。理由：抢滚动位置会打断三件事 ——
  ① 正在选中文字准备复制（选中丢失）② 正在看长内容（得重新滚回去）③ **正在往上翻历史（永远翻不上去，
  消息越频繁越没法用）**。这也是微信 / Telegram / Slack / Discord 的通行做法。
- 但补了一个边界：**自己发的消息，无论你当时翻在哪，一定滑到底部**（你发的东西你肯定要看）。
- 三种行为并存：自己发的 → 一定到底；别人的 + 你在底部 → 跟随；别人的 + 你翻在上面 →
  不打扰，浮「N 条新消息 ↓」。

**验证：** 新增 `dev/scroll-check.py`，**17 项断言**（初始在底部 / 翻上去不被打断 / 按钮文案带条数 /
点按钮滑到底 / 在底部时自动跟随 / 自己发消息一定到底 / 桌面版同样行为）。
桌面 21 + 手机 22 + 滚动 17 **全部通过**。

## 2026-10-06 · 剪贴板模式："被拒绝"其实是僵尸提示

**原话：**

> 剪贴板读取被拒绝

> 这个是不是有timeout啊，为啥我明明检测到了发出去了但是还是显示被拒绝

**根因（一句话）：** 消息**确实发出去了**，但早期那次失败留下的**警告没有在恢复后清掉** ——
`readClipboard()` 成功时只清了 `lastError`，没调 `setWarn('')`，
于是界面上留了一条"明明已经好了还在报错"的僵尸提示。

**顺带查出并修掉的四个问题：**

| # | 问题 | 修法 |
| --- | --- | --- |
| 1 | `readText()` 一抛错就 `supported = false` **永久放弃** | 区分**永久性**（无 API / 非安全上下文）与**可恢复**（未授权 / 未聚焦）；可恢复的保持轮询，并给「重试」按钮 |
| 2 | **判断顺序反了** —— 非安全上下文里 `navigator.clipboard` 直接是 `undefined`，会误报"浏览器不支持这个接口" | 先判 `isSecureContext`，再判 API 是否存在 |
| 3 | **僵尸提示**（本轮主因） | 读成功时**连警告一起清掉**；同一种错误不重复刷屏 |
| 4 | **纯文字模式下，别人的消息也会覆盖你本机剪贴板** | 只在**剪贴板模式激活时**才回写（`state.modeId === 'clipboard'`） |

**另外加的：**
- 状态条上一行**诊断**：`安全上下文 ✓ · 页面聚焦 ✓ · 权限 denied · 最近错误 NotAllowedError`
  —— 一眼看出是"没聚焦"还是"没授权"，不用猜；
- 「重试」按钮（用户手势里调用最可靠，能顺势带出授权弹窗）；
- 页面重新获得焦点时**立刻重试一次**，不用等下一个 800ms 周期；
- `permissions.query({name:'clipboard-read'})` 的 `onchange` 监听 —— 你去地址栏改权限后界面自动跟着变。

**关于 timeout：** `navigator.clipboard.readText()` **本身没有超时参数**，它要么立刻给文本、要么立刻 reject；
我们的轮询是**每 800ms 一次，失败下一轮再试，不超时也不放弃** —— 这正是想要的：
点了「允许」之后最多 800ms 自动恢复。

**验证：** 新增 `dev/clipboard-check.py`，16 项断言，其中 **①b「中途授权 → 警告必须自动消失」**
就是这次的回归测试。全量：桌面 21 + 手机 23 + 滚动 17 + 剪贴板 16 = **77 项全部通过**。

## 2026-10-06 · 剪贴板支持图片与文件 + WebSocket 容错

**原话：**

> 复制图片不行

> 顺便把复制文件也加上，如果ws走不了的就直接拒绝请求不要崩溃

**一、剪贴板图片：读的根本不是同一个 API**

老实现只调了 `navigator.clipboard.readText()` —— 它**只能读文本**，图片压根没被检测到。
读图片要用 `navigator.clipboard.read()`（一次拿到剪贴板里所有类型）。
分工是：`readText()` 全浏览器都支持但只读文本；`read()` 能读图片但 Firefox 没有。
所以：**有 `read()` 就用它，没有就退回 `readText()`**（退回时界面上写明"这个浏览器读不到图片"）。

**二、剪贴板文件：浏览器有硬限制，只有一条路**

| 通道 | 能读到什么 | 说明 |
| --- | --- | --- |
| `navigator.clipboard.read()`（轮询用） | 文本 + 图片 | **拿不到**从资源管理器复制的文件 |
| `paste` 事件（用户按 Ctrl+V） | 文本 + 图片 + **文件** | 唯一能拿到文件的路 |

原因不是本项目没做，而是**浏览器的安全边界**：网页不能随便读你磁盘上的文件，
否则任何页面都能把你硬盘里的东西读走。所以实现成：
- 轮询路径照旧抓文字和图片；
- 额外挂一个 `document` 的 `paste` 监听 → 从 `clipboardData.files` 拿文件 → 上传发出；
- 轮询里如果识别到 `text/uri-list`（`file:///` 路径），**明确告诉用户"按 Ctrl+V"**，而不是静默什么都不做。

**三、WebSocket 容错："走不了就明确拒绝，不要崩"**

这一条查出了**两个真 bug 和一个安全漏洞**：

| # | 问题 | 修法 |
| --- | --- | --- |
| 1 | 客户端：`ws` 置空后，4 秒超时的定时器还在引用它 → `Cannot read properties of null`，未捕获异常 | 所有监听器/定时器**抓住当时的 socket 实例**（`const sock = ws`），绝不用外层可变的 `ws` |
| 2 | 客户端：回执不区分是哪条请求 —— 同时发两条，第一条的 ack 会把两条都解决掉 | 每条请求带唯一 `id`，服务端 ack/error **原样回带**，客户端按 id 匹配 |
| 3 | **服务端：大小限制只在 HTTP 路由里校验，WS 那条路整个绕过** —— 走 WS 发 70KB 文本不会被拒绝 | 校验收口到 `room_store.push()`（两条上行路径的唯一汇合点），HTTP 翻译成 413，WS 翻译成 error 帧 |
| 4 | 服务端：`send` 处理时抛异常 → 异常冒出循环 → **整条长连接被拆掉** | 每条消息单独 try/except，失败只回一个 error 帧，连接继续用 |
| 5 | 服务端：`receive_text()` 遇到二进制帧会直接抛异常拆连接 | 改用 `receive()` 自己判类型，非文本帧回 error 帧 |
| 6 | 客户端：连接断开后在途请求要干等 4 秒超时 | `onclose` 里**立刻 reject 所有在途请求**，调用方马上拿到明确错误 |
| 7 | 前端：`submitText()` 没有 catch，发送被拒时变成未捕获的 Promise 异常 | 加 try/catch，**并把内容放回输入框**（别让用户白打一遍） |
| 8 | 错误提示带原始响应体（`HTTP 400 {"detail":"..."}`） | `api.js` 从 `detail` 抽出那句话，只显示人能看的 |

**验证：** 新增 `dev/ws-check.py`（19 项：协议层直连 + 浏览器层），
`dev/clipboard-check.py` 扩到 25 项（图片自动发 / 同一张图不重复发 / Ctrl+V 文件 / 不支持的类型明确拒绝）。
全量：桌面 21 + 手机 23 + 滚动 17 + 剪贴板 25 + WS 19 = **105 项全部通过**。

## 2026-10-06 · 单元测试（103 项，1.2 秒）
