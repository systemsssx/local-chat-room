我的开发经历 · 局域网协同剪贴板

2026-10-06 晚上做的，前后四个小时（20:00 开始，次日 00:17 结束，跨度 4 小时 23 分）。 技术细节在《开发经历总结》里，我跟 AI 的完整对话在《对话记录 01 · 实现过程》。

先把分工说清楚

一开始就说好：我出思路，它写代码，README 里能看出我的思路。

这么定是有原因的。这题要交付的东西我自己得讲得清楚，所以定了个规矩：不懂的地方不拍板，先问明白再决定。 实际做下来代码基本都是它写的，我这四个小时里花时间最多的其实不是写代码，是问问题 —— 下面第二节专门记这件事。

一、我做的几个决定

先把我拍过板的东西列一下，后面的内容基本都围着它们转。

决定我凭什么定的
范围：三个任务全做 + SQLite 历史 + 系统剪贴板自动同步题目里这些是分开的任务，我想要的是一套东西能跑通全流程，而不是三个互不相干的小 demo
界面骨架：六个组合 = 2 种输入 × 3 种传输，四面框两种输入方式和三种传输本来就是两回事，组合起来才是 6 种。这不光影响界面，也决定了后面代码怎么拆
六个组合共用一份数据源如果每个组合各存一份消息，那"历史互通"就是假的。所以先定死：切换只换管道和输入方式，消息只有一份
交互模型从"共享输入框"改成"聊天室"数据源在服务端，就不再是"多人共用一个输入框"，而是一台设备往里发东西、所有人看到同一份历史
不做输入防抖接着上一条：这题不是逐键同步，是"内容确认后才发一条"，没有需要防抖的场景
数据存服务端追问清楚"数据源在哪台电脑上"之后才定的。存本地就没有协同可言
换成 Python（FastAPI）+ 多文件结构题目首推的就是 Python；多文件是为了结构清楚，别堆在一个文件里
交付不做 exe，做"双击启动 + 手机能连"我要的是那个交互，不是 .exe 这个后缀。真 exe 每改一次代码就得重打，不划算
手机单独出一版桌面版是四面框，手机竖屏放不下，压扁了没法用
P2P 那道题的结论：不做聊天室要历史、要权威，这些只有服务端能给；再加 P2P 只是多一套复杂度

这些决定里有几个是我先想出来、再去跟 AI 对齐的；也有几个是听它讲完之后才定的。下面按做的事儿的顺序记。

二、靠提问把不懂的地方弄明白

这是我这四个小时里做得最多的一件事，单独记一下。

为什么这么干

不懂的地方拍板，后面一定要返工。所以我的做法是：碰到不认识的词、不确定的设计，先问到能用自己的话讲一遍，再决定怎么做。 有几次问得比较久，但问完确实省事。

例子一："双向"这两个字，问了五轮

题目里反复说"双向"，我一开始真不确定指什么，连着问了五轮，中间还猜错：

我问的当时我的理解
什么是双向不知道
文本修改通过 WebSocket 发送，所以双向发生在这步是吗以为是"发消息这一步"
也就是说双向的意思是服务器原来没有编辑本地端的权限，现在有了？猜的，不对
哦懂了，前两种要什么数据只能本地端找服务器问，后一种相当于本地端和服务器坐在同一张桌子吃饭这下差不多对上了
SSE 多了新数据会触发逻辑、服务器推给你，你要走另一条通道传数据；WebSocket 里这两条通道是一条通道自己复述一遍才算清楚

这一步的产出：搞清楚了三种传输的本质差别 —— 前两种下行靠服务端推、上行还得另开一条路，WebSocket 是上下行同一条连接。后面 README 里"三种方式的区别"那节、还有后端为什么只有 WS 那条路上行也走 socket，都是照着这个判断写的。

例子二：局域网到底是怎么连上的

后端开工我提的要求是"先搞定局域网连接，解释一下局域网内是怎么连接上的"，然后一路往下问：

  • ARP、TCP 是啥？→ IP 转 MAC 由内核查 ARP 表，三次握手也是内核做的
  • 局域网里握手的是谁？这些 ARP、TCP 啥的？→ 分层：应用代码只管发请求，下面几层是操作系统
  • 那我握手需要的只是调用操作系统去发送请求的代码吗？ → 是，应用代码不碰 ARP/TCP

这一步的产出：知道网络这层我只需要管到"应用层怎么发请求"，下面几层是内核的事。后来手机连不上时，我第一反应是去查防火墙规则，而不是去改代码 —— 因为连接失败的原因大概率在系统层，不在应用层。（实际查下来 python.exe 的入站规则确实覆盖了 Public profile，而这台机器的 WiFi 正好被 Windows 归成"公用网络"。）

顺带还问了分帧。我问的原话是：

之后自己解析 WebSocket 帧：opcode、掩码、payload 长度、分片重组，这个逻辑还有什么别的地方有用到吗？有人帮我干过的事我为什么还要再干一遍？

问完才分清：帧的编解码是浏览器和库的事，但"TCP 之上怎么划分消息"这个问题本身得懂，不然不知道 WebSocket 替你解决了什么。长度前缀我是用大白话确认的："那 2 就是先告诉你这条消息有多少字，然后让机器去算是吧"。

例子三：库到底是什么形式

轮到我拍板存数据的时候，我的问题是：

OK，现在建库吧。你告诉我库是什么形式的（CSV 吗，那图片怎么办），第二个他的接口是怎么接的。

这一步的产出：CSV 不行（没事务、并发写会坏）；图片不该入库（二进制放磁盘，库里只存 URL 和元信息）；接口就是两张表 —— 房间当前状态 + 历史记录，靠 seq 去重。最后落地就是 data/app.db 一个 SQLite 文件，拷走它就等于备份。

例子四：换 Python 之后冒出来的一批概念

换栈是我拍的，但我那时候对 Python 的 Web 框架基本一无所知，所以又是一轮逐个问：

  • FastAPI 干嘛的？ → 它不写业务，负责把 HTTP 请求翻译成 Python 函数调用
  • config.py 为啥要单独写一个 py？他是负责生成 .config 的吗？ → 猜错了，它不生成任何文件，它本身就是配置
  • 这个写法跟我写一个本地的程序带有上网请求的好不一样 → 差别就是客户端"我调用别人"、服务端"我被别人调用"
  • 那我客户端和服务端要分别打包成两个不同的程序？ → 不用，客户端就是服务端托管的那几个网页文件
  • 你给我的 html 界面是服务端还是客户端，应该是客户端吧，那服务端的启动入口在哪？ → 是客户端；入口是 server.py
  • 我 npm run build 打包出来的结果是什么？ → 这项目零构建，public/ 本身就是产物

这一步的产出：搞清楚了这个项目里"谁是客户端、谁是服务端、交付的时候交什么"。所以后来我提"双击启动 + 手机能连"的时候，目标很明确 —— 要打包的就是服务端那一份，客户端不用管。

"跟我写一个本地的程序带有上网请求的好不一样"这句是我自己比出来的。

三、界面这块改了三回

这块主要问题在我，一开始没说清楚。

第一次，我给了一张手画的草图和一个参考项目：

我要侧边栏有三个板块，每个板框两个小栏……ui 参考 C:\work\epubui\EasyPub-New 的 index.html，侧边栏按他的写法，小栏就模仿书库功能中的本地图书和精选推荐。

它理解成"文字 / 历史 / 图片"三块，猜错了。

第二次我说清楚：

我的意思是三种大栏做侧边栏，对应三种功能，纯文字和读取放上面作为上面的选择栏，一共 2×3 六种组合……中间的空白部分再做一个信息显示窗口，下面是输入框（如果是读取剪贴板就没有输入框）……做成聊天式的形式，一条信息横向要占满。

第三次又补一句：

说错了，是上下左右侧边栏。

到这儿骨架才定下来：上面是纯文字/剪贴板，左边三种传输，下面输入，右边成员·服务·历史，中间信息窗口。

这轮我还提了一件对后面影响比较大的事：

我想的是六个板块的互通问题，怎么让六个板块共用一个信息窗口，切换的只是发送信息的模式（历史记录也是互通）。

这句话后来变成了前端的架构：一份数据源，切换只换"管道"和"输入方式"两根轴。如果一开始我就把这两根轴讲清楚，前面大概能少改两回 —— 这是我这次做得不好的地方。

四、交付形态：双击启动 + 手机能连

我先问有没有双击启动的 exe。它说真 exe 要打包、改代码得重打，我就把目标说清楚了：

我现在要的是，我 exe 启动服务端，然后我在手机上输入网址，可以连接上这个服务器。

再补一句：

不用，假的 exe 也行，但就是我要的这个交互逻辑。

所以最后做的是 启动服务.cmd 加一份防火墙放行脚本，没去打包。

手机那边我提的是：

你针对手机做一个适配版 html。

桌面版四面框在手机上放不下，所以做成顶栏 + 组合条 + 全宽消息流 + 底部输入，左右侧栏收进两个抽屉；窄屏访问根地址会自动跳过去。

五、用起来发现的问题

这几处是我自己用的时候觉得不对、报给它查的。修都是它修的，我负责说现象和追问。

① 自动滚动其实是坏的

更新一个小点，现在有最新消息会下滑到底部

查下去发现比我说的问题还大：自动滚动一直没生效过 —— 代码在给 #streamList 设 scrollTop，但真正能滚的是它爸 #msgs。

② 发消息时到底会不会滑到底部

它说"你自己发消息时也不会拽到底部"，我记得是会，就回了句"会啊"。后来它承认上句说得太绝对：在底部时确实会拽，不拽的只有"先翻上去、再发消息"这种边缘情况，然后把那块补上了。

③ 剪贴板"被拒绝"

我先报的是"剪贴板读取被拒绝"。它改完一版之后我又补了一句：

这个是不是有 timeout 啊，为啥我明明检测到了发出去了但是还是显示被拒绝

后来查出真因是：消息其实发出去了，是失败时留下的那行红字没被清掉，一直挂在界面上。

④ 复制图片不行

查出来老的实现只调了 readText()，它只能读文本，图片根本没检测到，得换成 navigator.clipboard.read()。

⑤ 复制文件 + WS 不崩

顺便把复制文件也加上，如果 ws 走不了的就直接拒绝请求不要崩溃。

后半句查出一个漏洞：64KB 的大小限制只在 HTTP 路由里校验，WebSocket 那条路整个绕过去了。修法是把校验收口到 room_store.push()。另外服务端改成单条坏消息只回个 error 帧、不断开连接。"复制文件"最后发现是浏览器的安全边界（网页不给读本地文件），只能靠 Ctrl+V。

六、P2P 那道题

听完它讲 WebRTC 那一套，我先把结论说了：

所以 P2P 没有性价比的原因是因为我做了聊天室型的交互模式是吗？

它回了个"一半对"，又铺开讲了信令、STUN/TURN、端到端加密一大套。我把话说直了：

我的意思就是这个，聊天室要求有服务器，有服务器就不好用 P2P，为什么你总是理解不了我的意思呢

这句我说得有点急。不过我的意思确实一句话就能说完：

聊天室 → 必须有服务器（存历史、当权威） → 服务器本来就在内容路径上
       → 再引入 P2P 只是多一套复杂度

后来 README 里这道题就按这条主线写。

七、单元测试

我先问的是概念：

你先别急，单元测试的意思是就是比如我测试一个 py 脚本跑不跑的动吗？

搞清楚"跑得动"和"喂各种输入看返回对不对"不是一回事之后才让它写。最后 103 个用例、1.25 秒跑完，用 Python 标准库 unittest，每个用例都拿临时数据库。

这块我拖晚了。要是早点写，前面"冷房间第一条重复"和"WS 绕过大小限制"这两个坑，写的时候就能发现。

九、还没做好的地方

  1. 界面口径一开始没讲清，改了三回，也是这四小时里最耗时的一段。两张轴（输入方式 × 传输方式）应该第一句就说。
  2. 测试写晚了。两个真 bug 本来在写的时候就能发现。
  3. 有几个问题跟本题关系不大（微信为什么限 1GB、分片重组的细节），属于顺带了解，占了一点时间，不过也没影响进度。
  4. 分工上我偏"定方向"，界面骨架、交互模型、范围这些是我拍的，具体代码基本是 AI 写的 —— 这点我照实说。
